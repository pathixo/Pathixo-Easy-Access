## 10. SECURITY ARCHITECTURE —

NON-NEGOTIABLE Security must be treated as a core architectural requirement, not a final cosmetic feature. The application must be designed to resist common web application attacks and unauthorized data access. DATABASE SECURITY Enable Row Level Security (RLS). Deny public access to visitor records. Deny public access to reward inventory. Restrict administrative queries. Use least-privilege database permissions. Never expose Supabase service-role keys. Keep secrets on the server. Use parameterized queries. Validate all inputs server-side. API SECURITY Validate request payloads. Apply rate limits. Prevent unauthorized admin API calls. Validate visitor eligibility on the server. Prevent IDOR vulnerabilities. Prevent mass assignment. Protect against replay attacks. Use secure idempotency handling. Restrict CORS to approved origins where applicable. APPLICATION SECURITY Implement protections against: SQL Injection. Cross-Site Scripting (XSS). Cross-Site Request Forgery (CSRF), where applicable. Broken Access Control. Brute-force attacks. Credential stuffing. Spam registrations. Automated bot submissions. Session hijacking. Sensitive data exposure. Duplicate reward claims. Race conditions. Use secure HTTP headers, including an appropriate Content Security Policy, HSTS on HTTPS, and frame restrictions. Use secure, HttpOnly, SameSite cookies for authenticated sessions where applicable. Do not store administrator authentication tokens in localStorage. PRIVACY Collect only necessary information. Show a clear privacy notice. Obtain appropriate consent. Restrict personal data access. Provide a reasonable retention policy. Avoid exposing PII in application logs. Avoid including personal information in public URLs. Keep exported data restricted to authorized personnel. IMPORTANT SECURITY PRINCIPLE No web application can honestly be guaranteed to be completely unhackable. Build according to secure engineering practices, test common attack surfaces, and document any remaining security limitations before deployment. 11. MULTI-USER CONCURRENCY AND SCALABILITY The expo platform may receive multiple visitors simultaneously. It must not assume that only one person will use it at a time. Implement: Stateless application architecture where practical. Efficient database connections. Indexed database queries. Pagination for admin tables. Atomic reward allocation. Transaction-safe registration. Duplicate submission protection. Proper request timeouts. Graceful error handling. Retry-safe operations. Caching for public product information. Server-side authorization on every protected operation. Use database transactions and constraints to maintain data integrity. The same visitor must not receive multiple spins because of simultaneous requests. The system must not lose successful registrations during traffic spikes. Do not claim that the system can support a particular number of concurrent users without testing it. Run basic load and concurrency tests before the event.
